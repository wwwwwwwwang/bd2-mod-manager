### 修掉的一个真 bug

首轮卸载后残留 `BepInEx\`、`BepInEx\plugins\`、`BepInEx\Translation\ar\` 等空目录。

原因：`Directory.CreateDirectory(叶子目录)` 会连带创建所有父目录，但状态文件只记录了 manifest 里的叶子目录，
中间层没记录 → 卸载时漏删。

修复：新增 `EnsureDir()`，逐级创建并记录**每一层**新建的目录；卸载时按深度倒序删除。
另外补了 `PruneEmptyBaseDirs()`，顺手清掉自己建的空状态目录。

## 七、第三方组件（0.3.0）

目标：工具不再只管 loader，还能把使用者自备的第三方插件「装进来、管起来」，但不把别人的二进制塞进我们的发布物。

**设计**：一个组件 = `BepInEx/plugins/<名字>/` 一个子目录；逐文件记 sha256；loader 自带的插件（ConfigurationManager）不接管；关闭「启用 Mod 支持」时先清组件再删 loader。

**服务器实测**（`/tmp/g2`，`XDG_DATA_HOME` 隔离状态目录，源码 `远端 Linux 构建机（`ssh <构建机>`, 目录 `~/bd2mm-build`）`）：

| 步骤 | 结果 |
|---|---|
| `component-install /tmp/g2 皮肤解锁/` | 自动识别 `BepInEx/plugins` 子树 → 装成 2 个组件（单文件插件 1 个、多文件插件包 1 个）；ConfigurationManager 判定为 loader 自带并跳过 |
| `components` | 两项，显示文件数、体积、来源路径 |
| `component-disable <第三方插件>` | `插件.dll` → `.dll.disabled` |
| `component-enable` | 改回 `.dll` |
| `component-remove <多文件插件包>` | 23 个文件连空目录一起清掉，另一个组件不受影响 |
| `uninstall` | 组件与 loader 一并清除，`/tmp/g2` 只剩 `BrownDust II.exe` 与 `BrownDust II_Data` |

**图形界面实测**（Xvfb + scrot + xdotool 真点击）：

| 操作 | 结果 |
|---|---|
| 启动 | 「第三方组件」卡片列出 2 项，组件内的 dll 不再重复出现在「插件」列表 |
| 点组件开关 | 行内变灰、副标题转「已禁用，不加载」，磁盘上确认改名成功 |
| 点「移除」 | 弹确认框；确认后目录被删、卡片剩 1 项、日志写「已移除组件 <第三方插件>」 |

期间修掉的问题：初次实现会把 ConfigurationManager 当成组件接管（会与 loader 记录冲突），已加「由加载器自带则跳过」；组件内子目录原本被拍平，改为保留相对路径。

## 八、自研解锁插件（0.4.0）

目标：解锁功能由一份自己写的 MIT 插件承担，不带任何许可证负担。

**构建链**（关键是把「编译期引用」和「运行期版本」分开）

| 依赖 | 来源 | 理由 |
|---|---|---|
| `BepInEx.dll` / `0Harmony.dll` | 从我们自己组的 loader 包里拆（`scripts/prepare_refs.py`） | 必须与用户实际运行的版本完全一致 |
| `UnityEngine.Modules 2021.3.33` | NuGet，`ExcludeAssets="runtime"` | 只要编译用的元数据，不进产物；版本与游戏的 2021.3 同线 |

`netstandard2.0` + 上面三个引用即可编译，**不需要游戏本体**，所以 CI 能出包。本机实测：缺 `UnityEngine.dll`
（聚合 facade）会报 CS0012，加上后通过；`PackageReference` 方式能自动处理 TFM 与前向，手工 HintPath 到
`lib/netstandard2.0/` 则不行。

**离线验证**（`tests/BD2ModManager.SkinUnlock.Tests`，假游戏结构，本地 31 项 / CI 32 项）

| 段 | 覆盖 | 结果 |
|---|---|---|
| 反射解析 | 从假 `Proto.Net.CostumeDBInfo` 等类型反查到字典、属性、`SetSkin` | 全部命中 |
| 皮肤目录 | 读 `PrestigeSkinTable` → 2 件服装 / 4 套皮肤 | 正确 |
| 注入 | 补 3 条、不重复补、不动游戏原有条目 | 正确 |
| 补全列表 | 服装 1001 从 1 条变 3 条，服装 1002 从 0 条变 1 条，重复查询不追加 | 正确 |
| 拦截点击 | `SetSkin` 前缀返回 false，原方法调用次数 0，回调仍触发，选择被记录 | 正确 |
| 回放 | 服务器把 `DesignId` 冲成 0 后，一轮巡检写回 2002；值已正确时不再写 | 正确 |
| 取消 / 回滚 | 取消后回到默认并清记录；回滚后字典只剩游戏原有那 1 条 | 正确 |
| 撤销补丁 | 卸载后列表回到 1 条 | 正确 |

**过程中修掉的问题**

1. 局部变量名把 Harmony 前缀的返回值语义写反（返回 false 表示跳过原方法），导致两条断言误报 —— 是测试的 bug，不是插件的。
2. `Patches.Info/Warn` 遮蔽了 `BaseUnityPlugin.Info`（CS0108）→ 改名 `LogInfo/LogWarn`。
3. `UnpatchSelf` / `UnpatchAll(string)` 在不同 Harmony 发行版里签名不一致（HarmonyX 标记过时、标准版没有 `UnpatchSelf`）
   → 改为记录已挂补丁、逐个 `Unpatch(MethodBase, MethodInfo)`。
4. `harmony.Patch(...)` 的可选参数个数两版不同（HarmonyX 多一个 `ilmanipulator`），直接调用会把重载绑死在编译期那版
   → 改为反射调用 `Patch`，按运行时实际签名构造参数。顺带解决了「用户装了别的 Harmony 版本」的兼容问题。
5. 初次测试想复用 Unity 侧那份 HarmonyX 打补丁，在 .NET 8 上 `AccessTools` 静态构造必崩；沙箱 `/tmp` 又是 noexec，
   MonoMod 的 helper 库加载不了。最终测试宿主用 NuGet 版 Harmony，并把「挂载失败时插件不能崩」也做成一条断言。

**图形界面**

「第三方组件」区新增「安装内置插件」：插件 dll 构建时嵌进 exe，点一下就从内嵌资源写出临时目录、走正常组件安装流程。
Xvfb 实测结果：组件列表出现 `BD2SkinUnlock · 1 个文件 · 28 KB · 运行中加载`，磁盘落在
`BepInEx/plugins/BD2SkinUnlock/BD2SkinUnlock.dll`。装完会扫一遍 `plugins` 目录，发现同类的旧版解锁插件文件
就提示「两个不能同时启用」。

**CI 上补到了真实挂载**：GitHub Actions 的 `/tmp` 可执行，MonoMod 的 helper 库能加载，于是两处补丁是真正
`harmony.Patch` 到方法上的，走的不是直接调用补丁方法的兜底路径：

```
log  补丁已挂上：查询服装皮肤 → CostumeDBInfo.GetConnectedPrestigeSkinDBInfos
log  补丁已挂上：切换皮肤 → Database.SetSkin
[OK] 两个补丁都挂到了真实方法上
全部通过：32 项检查。
```

也就是说：反射查找、补丁挂载、Prefix 拦截（返回 false 跳过原方法）、Postfix 改写返回值、撤销补丁 —— 全部在真实
Harmony 上验证过。沙箱这边因为 `/tmp` 是 noexec 才只能走兜底路径。

**尚未验证**：真实游戏里的字段名、加载时机、弹窗行为。这层只能进游戏看 `LogOutput.log`；插件启动会逐步报进度，

## 九、残留清理：卸载后不再留空壳（0.4.1）

**现象**：关闭「启用 Mod 支持」之后，界面仍显示 `已存在（他人安装）· 检测到来源不明的 BepInEx`，
日志里三条「缺少 winhttp.dll / BepInEx/core / doorstop_config.ini」。用户看到的就是「你不是已经清理了吗」。

**根因**：0.4.0 卸载只删「安装清单里记录过、哈希仍匹配」的文件。而下面这些是 loader **第一次启动时自己生成**的，
从来没进过清单，卸载自然不会碰：

| 残留 | 大小 | 说明 |
|---|---|---|
| `BepInEx/cache/chainloader_typeloader.dat` 等 | ~650 B | loader 类型缓存 |
| `BepInEx/config/BepInEx.cfg` | 5.4 KB | loader 主配置 |
| `BepInEx/config/com.bepis.bepinex.configurationmanager.cfg` | 944 B | 配置管理器配置 |
| `BepInEx/LogOutput.log` | 4 KB | 运行日志 |

目录还在、清单已删，检测逻辑 `present = Directory.Exists(BepInEx)` 于是把它们判成「他人安装」——
本质是工具把自己留下的东西说成了别人的。

**修法**

1. `LoaderStatus` 增加 `CorePresent` / `ResidueOnly`：`winhttp.dll` 与 `BepInEx/core/BepInEx.dll` 都不在时，
   游戏根本不可能加载任何插件，判定为「仅剩残留」，不再说成他人安装。
2. `Uninstall` 增加「清运行时产物」一步：删 `cache` 目录、`LogOutput.log*`、两份 loader 自带配置，再自内向外删空目录。
3. 新增 `CleanResidue`：没有安装记录时也能清；但核心仍在就拒绝执行（那种情况必须走正常还原，免得拆坏一份能用的 loader）。
   白名单之外一概不动，`plugins` 下的第三方插件只报告、不删除。
4. 图形界面残留态显示「仅剩残留」，并露出「清理残留」按钮；命令行加 `bd2mm clean-residue`。
5. 顺带：残留态下打开「启用 Mod 支持」不再弹「目录里已有 BepInEx」的确认框——那本来就是自己上次的痕迹。

**回归测试**（新增 `tests/BD2ModManager.Core.Tests`，26 项全通过）

| 场景 | 断言 |
|---|---|
| 残留识别 | `Present=true`、`CorePresent=false`、`ResidueOnly=true`；不再出现「缺少 winhttp.dll」 |
| 残留清理 | 缓存 / 日志 / 两份 cfg 删除；`plugins/vendor.dll.disabled` 原样保留 |
| 清到底 | 插件删掉后再清一次，`BepInEx` 目录整个消失，状态回到「未启用」 |
| 完整循环 | 装 loader → 模拟产生缓存 → 卸载，目录条目数回到安装前，卸载日志里没有「仍有残留」 |

**真实目录实测**


## 十、开关点一次就失效、日志反复报「已是禁用状态」（0.4.2）

**现象**：插件开关点第一次有效，之后怎么点都没反应；日志里一遍遍刷 `✗ 该插件当前已是禁用状态。` `失败。`。
总开关、组件开关也一样，只是不容易察觉。

**两个原因叠在一起**

**1）切换后路径没跟着改**

开关就是给文件改名：`X.dll` ⇄ `X.dll.disabled`。切换成功后列表项里记的 `DllPath` 还指着旧名字，
下一次点击拿旧路径去判断，`SetPluginEnabled` 直接判定「已经是该状态」并返回失败，开关再被弹回去。

**2）日志框抢焦点，吞掉后续所有点击（真正的元凶）**

日志框为了「自动滚到底」用了这行：

```csharp
LogBox.CaretIndex = LogBox.Text?.Length ?? 0;
```

Avalonia 里给只读 TextBox 设 `CaretIndex` 会让它进入输入态、抢走焦点。
第一次点开关 → 操作成功 → 写日志 → 这行执行 → 焦点跑到日志框 → **之后窗口里所有开关的点击都收不到**。
所以表现成「一次有效，之后全哑」，而且从 0.2 引入自动滚动起就存在，一直影响总开关、组件、插件三类开关。

**修法**

| 位置 | 改动 |
|---|---|
| `PluginItem` | 切换成功后原地更新 `DllPath`（补/去 `.disabled`），不重建列表——重建会让控件绑定重挂，反而点不动 |
| `MainWindow.axaml.cs` | 自动滚动改成 `ScrollViewer.ScrollToEnd()`，后台优先级执行，只动滚动条，不碰光标与选区 |
| `MainViewModel` | 总开关跟随 `CorePresent`（残留态显示关闭）；列表文案区分「运行中加载 / 已启用，但 loader 未安装」 |
| `Core.Tests` | 新增「开关改名后旧路径必须失效」契约测试 |

**真机实测**（Windows，`SendInput` 模拟真实鼠标，逐次核对磁盘文件名）

| 操作 | 结果 |
|---|---|

## 十一、点了清理仍显示「仅剩残留」、日志看不全（0.4.3）

**现象**：点「清理残留」并确认后，状态还是「仅剩残留」；日志区只能看到几行，最新结果永远被切在底部。

**1）清理其实成功了，是判定写错了**

清理确实把 `cache`、`LogOutput.log`、两份 loader 自带 cfg 全删了。但 `BepInEx/plugins` 里还留着插件 dll
——那是用户的东西，工具按设计不删。而残留判定原来是：

```csharp
ResidueOnly = Present && !CorePresent;   // Present = BepInEx 目录是否存在
```

目录只要还在（因为插件在），就永远是「仅剩残留」。等于给了一个**清不掉的状态**，用户当然以为失败。

修法：新增 `HasTraces`，只有「本工具能清的运行时产物」（cache、日志、loader 自带配置、残缺的 core/winhttp）才算痕迹。

```csharp
ResidueOnly = Present && !CorePresent && HasTraces;
```

只剩插件时状态改为「未启用 · plugins 里还有插件，loader 还没装，游戏不会加载」，
清理没有可清对象时也明确说明「缓存与日志早就没了，plugins 里的插件不是本工具装的，保留原样」。

**2）日志区：换了三代容器**

| 方案 | 结果 |
|---|---|
| `TextBox` + `CaretIndex` 滚到底 | 抢走焦点，之后所有开关点击都被吞（0.4.2 已修，但滚动仍不准） |
| `ScrollViewer` + `SelectableTextBlock` + `ScrollToEnd` | 内容高度报的是视口高度，滚动条根本不出现 |
| `ListBox`（虚拟化）+ `ScrollIntoView` | 高度是估算值，只滚到倒数第三行；而且会冒泡把整页带着滚 |

最终：**日志区从内容流里拿出来，固定在窗口底部**，用 `ListBox` + 关掉虚拟化（`ItemsPanel` 换普通 `StackPanel`），
滚动只对列表内部的 `ScrollViewer` 调 `ScrollToEnd`。窗口高度 760 → 830，日志区 158。

**实测**（Windows 真机，SendInput 逐次点击并核对磁盘）

```
· 组件 BD2SkinUnlock 已禁用（1 个 dll）。
[08:44:38] 完成。
· 组件 BD2SkinUnlock 已启用（1 个 dll）。
[08:44:40] 完成。      ← 最后一行完整可见，正是第 4 次操作
```

| 项目 | 结果 |
|---|---|
| 组件开关连点 4 次 | `.dll → .disabled → .dll → .disabled → .dll`，全部正确 |
| 状态文字 | `未启用 · plugins 里还有插件，loader 还没装，游戏不会加载` |
| 总开关 | 灰色（关），与「loader 未安装」一致 |
| 日志 | 自动停在最新一行，不再被切 |

## 十二、卡片被撑出窗口、组件区排版散乱（0.4.4）

**现象**：第三方组件卡片里的说明文字一行铺到窗口右边缘被切掉、不换行；两个按钮贴着卡片右边框；
「无」孤零零悬在标题和按钮之间。日志区则是通栏贴边，和上面的卡片不是一套东西。

**根因**：外层 `ScrollViewer` 只设了 `VerticalScrollBarVisibility="Auto"`，横向仍按 `Auto` 处理。
横向可滚意味着**测量时给内容的是无限宽**，于是卡片里的 `TextWrapping="Wrap"` 全部失效——
文字不换行，一路把卡片撑破；按钮也被顶到卡片边框外面。

> 这类问题不会报错，只在「内容刚好比窗口宽」时暴露。之前几版窗口里的文字都短，所以没露馅。

**修法**

| 位置 | 改动 |
|---|---|
| 主 `ScrollViewer` | `HorizontalScrollBarVisibility="Disabled"`，内容宽度被约束成视口宽度，换行恢复 |
| 第三方组件卡片 | 标题与计数并排在左（计数做成小徽标，无组件时不显示），按钮在右；不再挤成一排四列 |
| 组件行 | 每行套一层 `#FAFBFC` 圆角块，与插件行同一套视觉 |
| 组件空态 | 换成占位块：标题「还没有第三方组件」+ 两句说明，不再只摆一行长文字 |
| 插件行 | 同样套圆角块，两张列表外观统一 |
| 日志区 | 从通栏底条改成 `Classes="card"` + `Margin="18,0,18,10"`，和上面卡片同宽同圆角 |

**实测**（Windows 真机截图，分别用空组件与含组件两套环境）

| 场景 | 结果 |
|---|---|
| 组件空态 | 占位块三行文字完整显示，无裁切；按钮全部落在卡片内 |
| 含 1 个组件 | 标题旁显示「1 个」徽标；行内「移除」与开关竖排对齐 |
| 日志区 | 左右边缘与上方卡片严格对齐，四周留白 18 / 10 |
| 整体 | 无任何文字或控件越过卡片或窗口边界 |

## 十三、插件行压在日志卡片上（0.4.5）

**现象**：日志区固定在底部后，插件卡片里靠下的行会画到日志卡片上面，两者重叠。

**根因**：内容区只用了一个 `ScrollViewer`，没有显式的裁切层。当内容比可视区高时，
`ScrollViewer` 并不会保证把溢出部分挡住，卡片就画到了下一个 Grid 行（日志卡片所在位置）上面。

0.4.4 还有第二个诱因：日志区固定占 150px，加上卡片 12px 间距，内容需要的 561px 超过可用的 529px，
**正好差一行**，于是每次打开都有一行插件被切在日志边界上——看着就像叠在一起。

**探针实测**（临时在 `Opened` 里打印各层 Bounds，验证完即删）

```
window    680 x 830
clipHost  0, 69.33, 680, 558.67
scroll    0, 0, 680, 558.67
logCard   18, 638, 644, 146.67
content   18, 16, 644, 526.67   （desired 555.33 → 溢出 28.67）
```

**修法**

| 位置 | 改动 |
|---|---|
| 内容区 | 外面包一层 `Border ClipToBounds="True"`，滚不下的部分必须裁在这里，不能画到下面的卡片上 |
| 日志列表 | 150 → 96，把纵向空间还给内容；常见情况（2 个插件 + 空组件）下内容刚好放得下 |
| 卡片间距 | 12 → 10 |
| 日志卡片 | 上边距 0 → 10，与内容区之间留出可见空隙，截断处读起来是「下面还有」而不是「叠在一起」 |

**实测**

| 场景 | 结果 |
|---|---|
| 680×830，2 个插件 | 两个插件行完整显示；插件卡片与日志卡片之间 10px 空隙；日志不被遮挡 |
| 压到最小高（680） | 内容在第三方组件卡片下沿干净截断，插件卡片整个进入滚动区，日志卡片完好 |
| 连点插件开关 3 次 | `ConfigurationManager.dll ⇄ .dll.disabled` 三次全部正确，日志停在新的一行 |

## 十四、日志最后一行被切掉半个字（0.4.6）

**现象**：日志框底部那一行只露出上半截，字被切了一半。

**根因**：日志列表的高度是拍脑袋定的 96 / 104，不是行高的整数倍。

探针打出来才看清，有两个坑：

```
# 内边距与边框都在 ListBox 上时
Height=104  →  viewport=101.33     ← 差的 2.67 是 ListBox 模板自己的边距
extent=18k  →  offset=18k-101.33   ← 偏移量带小数，上下各露半行
```

`ListBox` 的 `Padding` 会被算进滚动内容里，视口高度因此不是 18 的整数倍；
`ScrollToEnd` 得到的偏移量就带小数，顶端和底端都会切掉半行。

**修法**

| 位置 | 改动 |
|---|---|
| 日志框 | 边框与内边距挪到外层 `Border`，`ListBox` 自己 `BorderThickness="0" Padding="0"` |
| 列表高度 | `90` = 5 行 × 18 行高，视口实测正好 90 |
| 行高 | 模板里 `TextBlock LineHeight="18"`，列表项上下 `Padding="2,0"`，行高完全由 LineHeight 决定 |
| 兜底 | 窗口布局完后量一次真实视口，若不是行高整数倍就修正一次（正常情况 delta=0，不动） |

修完的探针数据：

```
extent=216.00  viewport=90.00  offset=126.00  height=90.00
```

全是 18 的整数倍。像素扫描确认五行文字高度都是 17px（完整字形），
上下都不再有半行。

**实测**：连点「重新检测」灌到 12 行日志，日志框稳定显示 5 整行，顶行与底行都完整。

## 十五、解锁插件功能补齐（1.1.0）

前一版只做了两条主线（补全皮肤列表、本地切换），这次把剩下的缺口补齐：
贴图回调兜底、拦截默认皮肤写入、脏条目清理与大厅互动场景。

### 补齐的部分

| 能力 | 做法 |
|---|---|
| 弹窗贴图回调兜底 | `LoadTexture` Prefix，把回调包一层，0.5 秒没回调补 `null`；不引用 UnityEngine，用「运行时取委托参数类型 + 泛型闭包委托」包，离线测试也能跑 |
| 拦截默认皮肤写入 | `AddPrestigeSkinDBInfo` Prefix，designId=0 或表里没有的直接不写 |
| 脏条目清理 | 每 3 秒清一遍 designId=0 与表里没有的条目，先记账，退出时把移走的原始条目放回 |
| 大厅互动场景 | 把 `LobbySettingItemTable` 里 `PrestigeSkinId != 0` 的道具补进道具字典（Type=25），记账以便回滚 |
| 查询时过滤 | `GetConnected` Postfix 先剔脏条目再补全，并把补的条目同时写进字典 |

### 关键实现点：`ref` 委托参数怎么改

`LoadTexture(int, ref Action<Sprite>)` 的第二个参数是 byref。插件编译期不引用 UnityEngine，
所以声明成 `(int, ref Action<Sprite>)` 行不通；改用 `object[] __args`（Harmony 会把写回
作用到 ref 参数上），再在运行期按真实委托类型造一个闭包：

```
参数类型 = __args[1].GetType()
Invoke 的参数类型 T = 该委托的 Invoke 形参类型
Delegate.CreateDelegate(委托类型, pending, Dispatch<T>)   // 得到签名正好是 void(T) 的委托
```

`Dispatch<T>` 只做一件事：拿到 pending 就触发一次，之后置为已触发。

### 离线验证从 32 项扩到 62 项

模拟环境新增 `SkinExchangePopupUI`（含 `ref` 委托参数）、`ItemDBInfo` + 道具字典、
`LobbySettingItemTable` + `GetAllLobbySettingItems`。新增覆盖：

| 场景 | 断言 |
|---|---|
| 贴图正常回调 | 转发一次、同一张图、不重复触发 |
| 贴图超时 | 0.5 秒内不动；超时补一次 `null`；补过之后真回调也不再来 |
| 拦截默认皮肤 | designId=0 被拦、表里没有的被拦、正常 id 放行 |
| 大厅场景 | 只补 `PrestigeSkinId != 0`、Type 写 25、重复调用不重复补、回滚移除 |
| 清理脏条目 | 移走 designId=0 与未知 id；回滚把原始条目放回 |

结果：**四个补丁在本机真实挂载成功**（`mounted == 4`），62 项全部通过。
这也顺带验证了 `object[] __args` 对 `ref` 参数的写回是有效的——否则贴图那组断言会失败。

### 一个刻意的差异

清理脏条目时先记账，`Rollback` 会把游戏原本的条目放回去。玩家看到的效果一样，
退出后内存更干净。

## 十六、「加载成功却毫无效果」的三条根因（0.4.8 / 插件 1.1.1）

症状：日志里有「v1.1.1 已加载」，游戏里却什么都没发生；`LogOutput.log` 和 Unity 的
`Player.log` 两条通道都在 `Awake` 之后彻底安静。用 `SkinUnlock.probe.log`（绕开
BepInEx 日志系统直接写文件）一次定位：

**根因一：BD2 会销毁 BepInEx 的 manager 对象。**
探针显示 `Awake` 完成后 0.66 秒就来了 `OnDisable` + `OnDestroy`，此后 `Update`
一次都不会被调用。`BepInEx.dll` 里明明调了 `DontDestroyOnLoad`（6432 行），但游戏
还是把它清掉了。结论：**在这款游戏里，任何依赖 `Update` 轮询的 BepInEx 插件都不会工作**。

**根因二：`OnDestroy` 里调 `Shutdown()` 等于自杀。**
对象被销毁时补丁刚挂上 1 秒不到，`Shutdown` 又把它们全撤了，日志表现为
「已挂载 4 个补丁」紧跟「补丁已撤销」。改成 `OnDestroy` 不碰补丁，只在
`OnApplicationQuit` 收尾。

**根因三：`SkinExchangePopupUI.LoadTexture` 的签名判断写反了。**
回调参数是值传递的 `Action<Sprite>`，不是 `ref`；只认 byref 就永远匹配不上。

对应修法：解析与挂补丁全部提前到 `Awake`；周期任务改由 `Application.onBeforeRender`
驱动（静态渲染回调，不依赖任何 GameObject，对象被销毁后照常触发）；补丁被调用时若
皮肤目录还没建好，现场读表建一次，不再依赖定时器。

**验证**：真机 4 个补丁全部挂上且不再被撤销，补出 16 件服装对应 16 套皮肤与
10 个大厅互动场景，玩家实测未拥有的皮肤出现在「更换皮肤」弹窗里。

**附带教训**：探针文件 `SkinUnlock.probe.log` 只在「卡住的原因」变化时写一行，
否则挂机一小时能刷出几十万行；它也必须进残留清理清单，否则卸载后会留下孤儿文件。
